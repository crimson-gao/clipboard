# Clipboard 项目目标文档

## 1. 项目定位

Clipboard 是一个仅面向 `macOS Apple Silicon` 的本地剪贴板应用。

它的核心价值不是“收集尽可能多的功能”，而是围绕高频复制/回贴场景，提供一个：

- 唤起快
- 搜索快
- 回贴快
- 行为稳定
- 本地优先

的桌面工具。

当前唯一实现路线为：`Tauri 2 + React + TypeScript`。

---

## 2. 目标用户与核心场景

### 2.1 目标用户

- 高频复制文本的开发者、设计师、运营人员
- 经常需要在多个应用间来回拷贝内容的 macOS 用户
- 需要快速查看、搜索、再次复制近期内容的重度剪贴板用户

### 2.2 核心场景

1. **快速找回刚复制过的内容**
2. **按关键字搜索最近历史**
3. **把某条记录重新复制并粘贴回原前台应用**
4. **收藏重要片段，避免被过期清理**
5. **查看图片或文件类记录，并在 Finder 中定位文件**

---

## 3. 第一阶段必须做到

### 3.1 功能目标

- 后台常驻运行
- 监听系统剪贴板变化
- 记录文本、图片、文件三类历史
- 历史本地持久化
- 全局快捷键唤起主面板
- 菜单栏图标与基本菜单操作
- 主面板支持固定 / 非固定两种模式
- 非固定模式下失焦自动隐藏
- 支持搜索、分页、收藏
- 支持重新复制历史记录
- 支持将选中内容粘贴回前台应用
- 支持文件类记录在 Finder 中定位
- 支持基础设置项：快捷键、快捷键开关、tray 显示开关

### 3.2 体验目标

- 唤起窗口响应明确
- 最近记录刷新及时
- 搜索结果稳定可预期
- 收藏与清理规则简单明确
- 出错时尽量退化为“不能做某动作”，而不是整应用不稳定

---

## 4. 第一阶段明确不做

- iCloud / 云同步
- 多端同步
- Windows / Linux 兼容
- 浏览器扩展
- 账号体系
- OCR、翻译、AI 摘要
- 复杂工作流编排
- 团队协作能力

这些都不是当前阶段的产品主线。

---

## 5. 技术目标

### 5.1 需要坚持的原则

- 单一桌面技术栈
- 系统能力尽量放在 Rust
- 前端只承接 UI 与轻量状态
- 尽量减少跨层重复状态
- 优先可调试、可维护，而不是一次性做“最完整”方案

### 5.2 当前采用的关键实现决策

- `Tauri 2` 作为唯一桌面壳层
- `React + TypeScript + Vite` 作为前端实现
- 本地 JSON 作为当前持久化方案
- 图片二进制落地到 app data dir
- 使用 macOS 原生窗口能力处理悬浮与失焦隐藏

---

## 6. 当前版本的设计边界

### 6.1 已经具备的能力

从当前代码结构看，项目已经具备并围绕以下能力组织：

- 剪贴板监听与历史写入
- 7 天自动清理非收藏记录
- 历史分页加载与分类计数
- 文本 / 图片 / 文件分类展示
- 收藏与清空当前列表
- tray 菜单与快捷键唤起
- 固定窗口与自动隐藏切换
- About 子窗口
- 基础测试与本地校验脚本

### 6.2 当前仍然接受的限制

- 文件类记录当前更偏“路径记录”而非完整 Finder 语义回贴
- 持久化仍是 JSON，历史量继续增长后可能需要升级
- 前端主状态仍集中在 `useClipboardApp.ts`
- command 层虽然已比早期清晰，但仍需继续防止膨胀

---

## 7. 成功标准

如果第一阶段达标，应该满足以下判断：

1. 用户可以稳定找回最近复制过的文本、图片、文件
2. 用户可以通过快捷键快速唤起面板并完成再次复制/回贴
3. 收藏内容不会轻易丢失
4. 主窗口在固定与非固定两种模式下行为一致
5. 本地数据结构简单、可读、易于调试
6. 代码结构能支持后续局部演进，而不是再次回到“大文件堆逻辑”状态

---

## 8. 后续阶段的进入条件

只有在第一阶段稳定后，才考虑进入下一步：

- 数据量和查询性能真的出现瓶颈，再评估 SQLite
- 文件类记录确实需要“原生对象级回贴”，再扩展 pasteboard 语义
- 图片预览、搜索体验存在真实瓶颈，再做性能专项优化
- 交互复杂度明显上升，再拆更细的前端状态模块

原则：**先把当前单机剪贴板体验做稳，再谈扩展。**
