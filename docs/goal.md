# macOS Clipboard App 目标文档

## 1. 项目目标

开发一个仅面向 `macOS Apple Silicon` 本地安装使用的剪切板应用。

应用常驻后台，监听系统剪切板变化，记录历史并持久化到本地。用户可以通过快捷键或主动打开方式唤起主界面。主界面悬浮在其他应用之上，支持固定悬浮，也支持点击窗口外区域后自动关闭。

在实现方式上，优先使用成熟的现成方案，尽量少造轮子。整体技术路线偏向 Web 技术栈，要求前后端分离、易于调试，渲染层可直接使用 Chrome DevTools 调试。

## 2. 产品范围

### 2.1 必须支持

- 后台常驻运行
- 监听系统剪切板并记录历史
- 本地持久化历史记录
- 全局快捷键唤起主界面
- 主界面悬浮在其他应用之上
- 支持固定悬浮
- 支持点击窗口外自动关闭
- 支持搜索历史记录
- 支持复制历史记录
- 支持将历史记录内容重新写回剪切板
- 支持收藏历史记录

### 2.2 第一阶段不做

- iCloud 同步
- 多设备同步
- Windows / Linux 兼容
- 浏览器扩展
- OCR、翻译、AI 摘要等增值能力
- 复杂账号体系
- 云端服务

## 3. 核心使用场景

### 3.1 剪切板采集

用户在任意 macOS 应用中复制文本、图片或文件引用后，应用自动记录到本地历史。

### 3.2 快捷唤起

用户按下全局快捷键后，主界面立即显示在前台，位于其他应用之上，并聚焦到搜索框。

### 3.3 快速搜索

用户输入关键词后，可以立即筛选历史记录。

### 3.4 快速复用

用户点击某条记录后，可执行以下操作：

- 复制该记录
- 将该记录重新写入系统剪切板
- 标记 / 取消收藏

### 3.5 悬浮交互

主界面支持两种模式：

- 固定悬浮：窗口保持显示
- 临时面板：点击外部区域自动关闭

## 4. 技术目标

### 4.1 总体原则

- 最小代价完成可用产品
- 优先复用成熟库和社区方案
- 主进程与渲染进程职责清晰
- 本地优先，不依赖远端服务
- 开发体验优先，便于使用 DevTools 调试

### 4.3 提交约定

- 每个小改动在被用户接受后，都应立即提交到 Git
- 提交应保持原子性，一个 commit 只表达一个清晰变更
- 提交信息应简洁明确，能够直接说明本次修改意图

### 4.2 推荐技术选型

#### 桌面壳

- `Electron`

原因：

- 对 `macOS` 桌面能力支持成熟
- 原生支持 `BrowserWindow`、`globalShortcut`、`clipboard`
- 渲染层天然可用 Chromium DevTools 调试
- 生态最成熟，遇到系统层问题更容易找到现成方案

#### 前端渲染层

- `React + TypeScript + Vite`

原因：

- 迭代快
- 调试体验成熟
- 组件化和样式管理方便
- 与 Electron 配合成本低

#### Electron 工程组织

- 推荐：`vite-plugin-electron`
- 备选：`Electron Forge + @electron-forge/plugin-vite`

结论：

- 当前项目优先用 `vite-plugin-electron`
- 原因是结构更轻、接入更快、与普通 Vite 工程更接近
- 如果后期需要更完整的打包流程，再评估切换到 `Electron Forge`

#### 本地持久化

- 历史记录库：`SQLite`
- Node 驱动：`better-sqlite3`
- 配置项存储：`electron-store`

原因：

- 历史记录天然适合本地数据库，不适合长期只放 JSON
- 搜索、分页、收藏、去重、清理策略都更适合用 SQLite
- `better-sqlite3` 简单直接，适合本地单机应用
- `electron-store` 适合保存窗口状态、快捷键、偏好设置等轻量配置

#### UI 层

- 优先自定义样式
- 只按需引入少量基础库

建议：

- 图标：`lucide-react`
- 日期处理：`date-fns`
- 列表虚拟化：`@tanstack/react-virtual`，仅在数据量明显变大后引入

结论：

- 第一阶段不要为了“现代化”而堆 UI 框架
- 现有界面风格已经比较定制化，继续用自定义 CSS 成本更低

## 5. 架构设计

### 5.1 前后端分离

这里的“前后端分离”在 Electron 内部落地为三层：

- 主进程：系统能力、窗口管理、快捷键、剪切板监听、数据库访问
- 预加载层：暴露安全 IPC API
- 渲染层：React UI，只关心展示和用户交互

### 5.2 职责边界

#### 主进程

- 创建和控制主窗口
- 注册全局快捷键
- 管理 always-on-top / show / hide / blur 行为
- 监听剪切板变化
- 写入和查询本地数据库
- 提供 IPC 接口给渲染层

#### 预加载层

- 通过 `contextBridge` 暴露受控 API
- 屏蔽 Electron / Node 细节
- 统一请求参数与返回数据结构

#### 渲染层

- 搜索输入
- 历史列表展示
- 收藏状态展示
- 复制 / 粘贴 / 收藏等交互
- 面板布局与动画

## 6. 剪切板监听策略

### 6.1 第一阶段推荐方案

主进程轮询系统剪切板。

实现方式：

- 周期性读取 `clipboard.availableFormats()`
- 对文本读取 `clipboard.readText()`
- 对图片读取 `clipboard.readImage()`
- 对文件场景优先存储可读元信息，必要时再扩展
- 通过哈希或内容摘要去重

### 6.2 为什么先不用更重的原生方案

- Electron 官方 API 提供读写剪切板能力，但没有稳定通用的剪切板变更事件可直接依赖
- 轮询实现简单、调试直接、跨渲染层边界最少
- 对个人本地应用来说，先用 `500ms ~ 1000ms` 轮询通常足够

### 6.3 后续优化条件

仅当以下问题真实出现时，再考虑引入原生模块或更深的 macOS 方案：

- 轮询性能开销明显
- 图片采集不稳定
- 文件引用场景需要更完整的原生格式支持

## 7. 数据模型建议

### 7.1 clip_items

- `id`
- `type`：`text | image | file | html`
- `content_text`
- `content_html`
- `content_blob_path`
- `source_app`
- `content_hash`
- `is_favorite`
- `created_at`
- `updated_at`

### 7.2 app_settings

- `key`
- `value`

### 7.3 设计说明

- 文本直接存数据库
- 图片建议落地到本地文件，再在数据库中保存路径和元信息
- 使用 `content_hash` 做去重
- 收藏只是一种状态，不单独拆表

## 8. 窗口与交互方案

### 8.1 窗口形态

- 单主窗口
- 默认隐藏
- 唤起时显示并聚焦
- 可配置 `alwaysOnTop`

### 8.2 建议行为

- 启动后驻留菜单栏或后台
- 快捷键触发时切换显示状态
- 非固定模式下，窗口失焦后自动隐藏
- 固定模式下，窗口失焦不自动隐藏

### 8.3 调试要求

- 开发模式保留 Chromium DevTools
- 主进程日志与渲染层日志分离
- 关键 IPC 请求打点

## 11. 风险与约束

### 11.1 已知约束

- Electron 自带剪切板 API偏读写，不是完整监听框架
- 全局快捷键可能和用户已有快捷键冲突
- 原生模块在打包阶段需要注意 Apple Silicon 兼容性

### 11.2 风险控制

- 第一阶段只做文本监听，避免图片和文件把复杂度拉高
- 先轮询，再决定是否需要原生事件
- 持久化先采用 SQLite 单机方案，不引入服务端

## 12. 结论

推荐路线如下：

- 桌面框架：`Electron`
- 渲染层：`React + TypeScript + Vite`
- Electron 集成：`vite-plugin-electron`
- 数据存储：`SQLite + better-sqlite3`
- 配置存储：`electron-store`
- 调试方式：Chromium DevTools + 主进程日志

这是当前约束下最符合以下目标的方案：

- 成本低
- 交付快
- Web 技术栈友好
- 便于调试
- 对 macOS Apple Silicon 单机场景足够实用
